# Отчет по безопасности проекта Spainza

## Коротко

Проект проверен как Flask-приложение с обычным JavaScript-фронтендом.

Что уже хорошо:

- в production используется Gunicorn, а не встроенный Flask-сервер;
- debug-режим запрещен в production;
- cookie авторизации ставится как `HttpOnly` и `SameSite=Lax`;
- CORS не открыт для всех подряд;
- загрузки файлов ограничены по размеру и проверяются по типу;
- файлы из `storage` отдаются через проверки доступа;
- SQL-запросы в просмотренных местах используют параметры, а не склейку строк.

Что исправлено в этом проходе:

- добавлена централизованная защита от cross-site state-changing запросов для cookie-auth API;
- добавлен явный режим доверия к reverse proxy через `TRUST_PROXY` и `ProxyFix`;
- прямое доверие к `X-Forwarded-Proto` для HSTS убрано;
- в CORS разрешен безопасный служебный заголовок `X-Requested-With`;
- Python-зависимости закреплены по версиям;
- добавлены regression-тесты на CSRF и spoofed `X-Forwarded-Proto`.

Что осталось сделать вручную или отдельной задачей:

- проверить историю Git и заменить секреты, если они могли утечь;
- убрать Tailwind CDN и inline-скрипты из production HTML без поломки публичных страниц;
- добавить secret scanning перед commit.

## 1. Секреты в `.env` файлах

**Серьезность:** высокая.

**Статус:** не исправлено автоматически, требуется ручная проверка и возможная ротация.

**Где:** `.env:1`, `.env:4`, `.env.production:8`, `.env.production:12`, `.env.production:15`, `.env.production:20`, `.env.production:31`, `.env.production:40`.

**Что найдено:** в локальных файлах есть значения для Telegram bot token, Google client secret, пароля базы данных, JWT secret, пароля bootstrap-admin и SMTP-пароля.

Сами значения в отчет не внесены, чтобы отчет не стал новой утечкой.

**Почему это опасно:** если эти файлы попадут в архив, backup, на сервер, в переписку или в историю Git, по ним можно получить доступ к внешним сервисам, отправке почты, Telegram-боту или подписывать токены приложения.

**Что важно:** Git сейчас показывает, что `.env`, `.env.production` и `.env.deploy` игнорируются. Это хорошо, но не доказывает, что секреты никогда не попадали в историю или деплой-архивы.

**Что сделать:**

- проверить `git log --all`, не попадали ли секреты в историю;
- если секреты могли выйти за пределы машины, заменить их во внешних сервисах;
- хранить production-секреты только на сервере или в secret store;
- добавить pre-commit проверку секретов, например `gitleaks` или `detect-secrets`.

## 2. CSRF для cookie-auth API

**Серьезность:** высокая.

**Статус:** частично исправлено.

**Где было:** `backend/app.py`, protected API middleware.

**Что было:** приложение принимало авторизацию из cookie `access_token`, но изменяющие запросы не имели общей CSRF-проверки.

**Что сделано:** добавлена централизованная проверка для `POST`, `PUT`, `PATCH`, `DELETE` на protected API. Запрос проходит, если он same-origin/same-site по Fetch Metadata, имеет `X-Requested-With: XMLHttpRequest`, или проходит same-origin проверку по `Origin`/`Referer`. Явный `cross-site` теперь отклоняется с `403`.

**Что проверить дальше:** если нужно максимально строго, можно перейти на полноценный CSRF-токен, который backend выдает фронтенду и проверяет на каждом изменяющем запросе.

## 3. Доверие к `X-Forwarded-*`

**Серьезность:** средняя.

**Статус:** исправлено в коде, нужно проверить production proxy.

**Где было:** `backend/app.py`, `_is_https_request()`.

**Что было:** приложение напрямую читало `X-Forwarded-Proto`, из-за чего клиент мог подделать HTTPS-признак, если backend доступен напрямую.

**Что сделано:**

- прямое чтение `X-Forwarded-Proto` для HSTS убрано;
- добавлен `ProxyFix`, но только при `TRUST_PROXY=1`;
- в `.env.example` и `.env.production.example` добавлены `TRUST_PROXY` и настройки hop count;
- в `docker-compose.production.yml` выставлен `TRUST_PROXY=1` для production-контейнеров.

**Что проверить на сервере:** backend-порт не должен быть доступен из интернета напрямую, а reverse proxy должен перезаписывать `X-Forwarded-*`, а не пропускать клиентские значения как есть.

## 4. CSP, Tailwind CDN и сторонние скрипты

**Серьезность:** средняя.

**Статус:** не исправлено в этом проходе, чтобы не сломать публичные HTML-страницы.

**Где:** `backend/app.py:65`, `frontend/index.html`, `frontend/ru/*.html`, `frontend/en/*.html`, `frontend/lk/support.html`.

**Что найдено:** публичные страницы сильно завязаны на runtime Tailwind CDN и inline `tailwind.config`. CSP также содержит `'unsafe-inline'`.

**Почему не исправлено сразу:** простое удаление CDN-скрипта сломает стили страниц. Безопасное исправление требует миграции публичных страниц на локально собранный CSS и выноса inline-скриптов.

**Что сделать отдельной задачей:**

- собрать Tailwind локально для всех production HTML;
- убрать `cdn.tailwindcss.com` из страниц;
- вынести inline-скрипты и inline handlers;
- после этого убрать `'unsafe-inline'` и лишние внешние домены из CSP;
- для оставшихся CDN-ресурсов добавить SRI, если ресурс статичный и версионированный.

## 5. Python-зависимости

**Серьезность:** низкая.

**Статус:** исправлено.

**Где:** `requirements.txt`.

**Что было:** зависимости были указаны без версий.

**Что сделано:** версии закреплены:

- `Flask==3.1.3`
- `waitress==3.0.2`
- `gunicorn==26.0.0`
- `psycopg2-binary==2.9.12`
- `PyJWT==2.13.0`

**Что можно улучшить дальше:** для production можно добавить lock-файл с hash-проверкой и регулярную проверку уязвимостей зависимостей.

## Рекомендованный следующий порядок

1. Проверить историю Git на секреты и заменить все, что могло утечь.
2. Проверить настройки reverse proxy на сервере.
3. Отдельной задачей мигрировать публичные страницы с Tailwind CDN на локальную сборку.
4. Добавить secret scanning в pre-commit или CI.
